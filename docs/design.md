# Design

Afterimage is a self-hosted server for TRMNL e-paper displays. It onboards devices, keeps their firmware current, renders screens from data, and answers each device's check-in with the screen its schedule calls for. It reports device state over MQTT and keeps no history of it.

It does not run TRMNL community recipes, host plugins for other people, or implement TRMNL's cloud management API.

## Principles

- **Faithful.** The device API follows TRMNL's published contract exactly, so every device running TRMNL firmware works unchanged.
- **Generated.** Device models, palettes, firmware lists and design tokens come from TRMNL's published sources; nobody copies their values into code.
- **Generic.** Components, interfaces and screen elements serve every device and data source. Facts about one device live in data, never in a code path.

## Contract

The Smithy model in `model/smithy/` is the single source of truth. One build generates the Rust server stubs (smithy-rs), the TypeScript client (smithy-typescript) and an OpenAPI document from it. No component defines an operation, shape or error outside the model.

| Service | Contract owner | Caller |
|---|---|---|
| Device API | TRMNL firmware | Devices |
| Management API | Afterimage | Web UI |

The device API mirrors the four device operations TRMNL documents: `GET /api/setup`, `GET /api/display`, `GET /api/display/current` and `POST /api/log`; firmware 1.8.18 calls all but `/api/display/current`. TRMNL publishes them in its OpenAPI document (`https://trmnl.com/api-docs/openapi.json`); `model/trmnl/device-api.json` is the excerpt that `tools/trmnl-excerpt` takes from it, and the conformance test fails on any operation, header, body field or response field that the generated document and the excerpt do not share. The model adds one operation of Afterimage's own, `GET /api/images/{name}` for the images check-ins name, which the conformance test lists as an addition.

Where the document and the firmware disagree, the firmware decides. Headers are text, because the firmware sends values such as `3000/3500` where the document says number; the server parses what it reads and treats a value that does not parse as unknown. Status values follow the firmware's handling of them, which behaviour tests replay with the headers and bodies the firmware builds. The conformance test compares operations, headers, body fields and success fields; error responses are outside it, and each one the model adds is documented on its operation.

## Components

Each component builds on its own and depends on the others only through generated code, except that any Rust component may use the shared library `crates/trmnl`, and the server links the renderer library `crates/render-typst`, which draws in its process.

| Path | Owns |
|---|---|
| `model/smithy/` | Smithy contract |
| `model/conformance/` | The conformance test and the extractor behind `tools/trmnl-excerpt` |
| `crates/trmnl/` | TRMNL firmware protocol (MAC addresses, reported readings, status values) and the snapshot of TRMNL's model and palette lists that `tools/trmnl-catalog` refreshes |
| `crates/server/` | Device and management APIs, accounts and sessions, schedule, SQLite persistence, MQTT publishing |
| `crates/render-typst/` | The render operation in Typst, with a component library that reads design tokens |
| `tools/tokens/` | Build-time generator of design tokens per render profile |
| `web/` | Web UI on the generated TypeScript client |
| `deploy/nix/` | Nix packages, the development shell and the NixOS module |

## Devices

1. **Setup.** The device joins Wi-Fi through its captive portal, configured with this server's URL, and calls `/api/setup` with its MAC (`ID`) and `Model`, which firmware before 1.8 sends empty; every check-in sends `Model` too, and the server keeps the latest. Every setup creates a new registration: an access key, stored only as a SHA-256 hash, and a six-character friendly ID, which the firmware shows. A user claims the device by entering the ID in the web UI. Setup never touches an existing registration, because the firmware's only way back from a lost key is status 500, which erases its saved Wi-Fi networks and every stored setting, the server URL included. Anyone on the network can present a MAC, so a spoofed setup only creates a registration of its own, whose code never appears on the real device's screen. A device that runs setup again shows its new code; claiming that code for a device of the account with the same MAC moves that device to the new registration with its name, settings and playlist, and drops the old registration; other unclaimed registrations of that MAC end on their own. Removing a device without a reset returns its registration to unclaimed, so the device shows its code again. At most 32 registrations wait unclaimed. One whose key never checks in ends 24 hours after setup, and one that stops checking in ends after 7 days; a powered device checks in at least hourly. A host on the network can still hold those places with registrations that keep checking in, until a user removes them in the web UI. In the same way, a flood of OIDC sign-in starts can push out a real one, since the server keeps the newest 64.
2. **Model.** A claimed device starts with a display chosen from TRMNL's `GET /api/models` and `GET /api/palettes`: the model whose name the firmware reports, or else, by the panel size the firmware sends at check-in, TRMNL's own hardware with the most grays, at the palette its bit depth gives. TRMNL publishes no mapping from the name a firmware build reports to its lists, so the choice rests on those published fields alone, and a user can change it. The firmware board for updates comes from TRMNL's firmware lists the same way.
3. **Check-in.** The device calls `/api/display` with its `Access-Token`, its MAC and its state (`Battery-Voltage`, `Percent-Charged`, `RSSI`, `FW-Version`); the server keeps the last known value of each reading. Only TRMNL X sends `Percent-Charged`, so for every other board the server estimates the charge from the voltage with TRMNL's own formula, which firmware 1.8.18 documents as the server's `percent_charged_calculation`. A claimed device gets status 0 with the image of the next current entry of its playlist, drawn at the check-in, and a `refresh_rate` that wakes it at its refresh interval or when the set of current entries changes, whichever comes first. The image URL (`/api/images/<name>`) uses the host the device checked in at; the firmware downloads it with its `Access-Token`, and only that device may. An image is named by a hash of its content, and the firmware caches by `filename`, so an unchanged screen costs no download. A screen that cannot be drawn as written leaves the device on its last image, or shows what went wrong when it has none, and the next check-in moves on to the entry after it; with nothing current, the device shows a screen saying so. An unclaimed device gets status 202, on which the firmware shows its friendly ID and polls on its own schedule, every 5 seconds at first and backing off to hourly. A key the server does not know also gets 202, because 500 would wipe the device; such a device keeps showing a code the server has dropped and needs a reset at the device, and the server logs its MAC. Status 500 is sent only when a user removes a device in the web UI and chooses to reset it. A server failure is an HTTP error, which the firmware retries. The server publishes the reported state to MQTT.
4. **Firmware update.** TRMNL publishes full flash images for every board it builds firmware for at `GET /api/firmware/flash`, newest release first; its over-the-air images (`GET /api/firmware`) cover only its own hardware, and their bytes are the app images inside the flash images of the same boards, so the flash list serves every board. A device's board is the one a user chose, or else the board whose name is the model the firmware reports: TRMNL publishes no other link between the two, the names differ for most boards (the Seeed kit's `xiao_epaper_display` is built as `seeed_OG_DIY_Kit`), and a board's model name changes between releases. The newest release of a board is its highest version without a variant suffix such as `-sensors`. An install request fetches the release's flash image, cuts the app image out at the app partition its partition table names, ends it where its own header says, and checks its checksum and SHA-256 as the bootloader does; the server keeps it in its cache directory under its SHA-256 and serves it at `/api/firmware-images/<SHA-256>.bin`, so devices without internet access update too. The firmware downloads it without a key or redirects (1.6.10 and 1.8.18), and the image is public anyway. The device's next check-in answer carries the request once, with `update_firmware` and `firmware_url` beside its screen; the check-in after that decides it by the version the device reports. Firmware 1.8 restarts and checks in at once when it installed the release; after a failure it checks in at its next wake and waits a day before it tries again. Firmware 1.6 restarts and checks in after any attempt and never waits, so a request sent at every check-in would restart a failing 1.6 device over and over. A check-in on a special function gets no request, since firmware 1.6 then ignores it. A variant release, such as `1.8.18-push-to-refresh`, counts as installed when the device reports the version it varies, which is all its build reports. Choosing another board withdraws a request the device has not received, including one whose image is still being fetched.
5. **Logs.** The server writes `/api/log` entries to its own structured log and stores none. It reads at most 64 KiB per request, writes at most 32 entries and 512 characters per field, and writes device text escaped so that it cannot add lines to the log. Requests are bounded but their rate is not: a host on the network that holds a key can fill the log, which is the same trust the network already has over the device API.

## MQTT

With a broker configured, the server publishes each claimed device with Home Assistant's device-based MQTT discovery: its battery (estimated as in step 3 where the firmware reports none), voltage, signal, last check-in and current screen as sensors, and its firmware as an update entity whose install command starts step 4 for the board's newest release. A device is keyed by its MAC, so it stays the same Home Assistant device across setups, and its link back leads to its page in the web UI; when accounts hold devices of one MAC, as after a device set up again is claimed elsewhere, the topics belong to the one that checked in last. Discovery, state and firmware topics are retained, and a fact the server does not know is left out, since Home Assistant drops a payload with a null where it reads text. The server publishes every device when it connects and when Home Assistant announces itself on its status topic, and one device at each check-in and change; removing a device clears its topics, and on connecting the server clears the retained topics of devices removed while the broker was out of reach. Every entity's availability follows the server's own status topic, which its last will sets offline. Whoever may publish to the broker may start an install, so the broker's access control is the boundary; a retained install command is ignored, since the broker would replay it at every connection. History belongs to whoever consumes the topics.

## Screens and playlists

A screen document holds its data sources and a tree of generic components. The components and their properties are shapes in the model, so the document reads the same as JSON, as YAML in the web UI's editor and in the API, and the server stores it in the model's serde form. A data source is an HTTP request answering JSON, such as a Home Assistant REST call. Text properties are MiniJinja templates (Jinja syntax, as in Home Assistant, with its `multiply` filter) that read each source by name, `now()` and `device`; a template that is a single expression keeps its value's type, so a chart's series can be a list. Data source requests also read `secrets.NAME`, values the deployment provides as `AFTERIMAGE_SECRET_NAME` environment variables; screens name them and never hold them. Every account may use every secret in its requests, so a deployment gives its secrets to everyone it lets sign in.

A device's playlist lists the screens it shows, each on some weekdays and between two times of day in the server's time zone. At each check-in the device shows the next current entry.

The first release defines the components that TRMNL's 30 published plugins use most: view and layout (rows, columns, grid spans, alignment, gaps), title bar, item, title, label, value, description, image and divider, plus line and bar charts and three behaviours: fitting a value to its box, clamping text to a line count, and ending an overflowing list with a count of what is hidden. Table, progress, rich text and maps follow when a screen needs them; no published plugin uses table or progress.

## Rendering

The server draws a screen in three steps. It sends each data source's request, with its templates rendered and the deployment's secrets available to them; it renders every other template against the answers, expanding each `each`; it fetches the images the screen names. The renderer then gets the resolved screen, the images' bytes, and the device's model and palette from TRMNL's `GET /api/models` and `GET /api/palettes`: width, height, scale factor, rotation, MIME type, image size limit and colors. That interface is the render boundary; the server draws at each check-in and for each preview, and keeps a device's images under `images/` in its data directory. Firmware 1.8.18 waits 15 seconds for the check-in's answer, so a drawing is bounded: its data sources and images are fetched at once, each image once, within 11 seconds; its templates run for at most 2; and it gives up, leaving the device on its last image, when it cannot start its templates or its render within 13 seconds of starting. A document expands to at most 2,000 components and 16 images, an `each` without a `limit` to 100 elements. Secret values are replaced by their names in every answer a source gives and in every problem, so neither the screen nor the editor shows one.

Typst implements the renderer in-process (`crates/render-typst`). Its component library lays a screen out at the model's size divided by its scale factor and draws every component from the design tokens of TRMNL's design system (MIT) for the device's profile: fonts, sizes, gaps, radii, and TRMNL's dither tiles for gray areas on 1-bit and 2-bit displays, so screens keep TRMNL's look. The result is rasterized at the scale factor, turned by the model's rotation, mapped to the palette's colors (on two-color palettes everything darker than 75% luminance is ink, so the thin strokes of pixel fonts survive), and written as a PNG of the fewest bits per pixel that hold the palette.

A build-time generator (`tools/tokens`) produces those tokens. It loads a pinned release of the compiled stylesheet in headless Chromium, and for every profile of the catalogue snapshot applies each public token (the 278 that the release documents) and the fills and slots components paint with to a probe element, and records the computed value: lengths in pixels, colors, font families, weights, and the dither tiles as SVG. It also copies the release's fonts with their licence notices. Chromium runs only in the generator, never during a render. Reading the Sass source or the compiled stylesheet directly would mean reimplementing the cascade: the stylesheet declares 5,254 custom properties across 62,375 selectors, with `:is()`, `:where()`, cascade layers and color, dark and theme modes.

On one measured screen, Typst rendered in 13 ms with a 19 MiB memory peak; TRMNL's design system in headless Chromium took 1.3 s and about 1 GiB, most of it loading its 19 MB stylesheet. On the device, the two renders were hard to tell apart.

Another engine replaces Typst by implementing the same interface and every component, for example as a separate service that runs TRMNL's design system; screens stay unchanged.

## Storage and accounts

SQLite holds accounts, sessions, personal API tokens, registrations (MAC, model, access key hash, friendly ID, end time, panel size, latest readings), devices (owner, name, display, refresh interval, current registration, playlist position, the image it shows, the firmware board a user chose), each device's latest firmware install request, screen documents and playlist entries. A device's images live under `images/` in the data directory; each check-in draws its image anew, and one whose file is lost is drawn again even while its screen fails. Firmware images live in a cache directory; one that is lost before its device downloads it is cut from TRMNL's flash image again, at most once every ten minutes for a device, and the cache drops an image once its request is decided, withdrawn or replaced, or its device removed. TRMNL's list is read when first needed and again once it is six hours old. A device page never waits for it and shows the firmware facts the list on hand gives; listing the boards, choosing one and installing wait for a list when the server has none.

Users sign in through OIDC or with a local password; either way the result is an account, and handlers and storage never see the method. The first account signs up with a password; further accounts come from the OIDC provider, whose client assignment decides who may sign in. A session is a random token in an httpOnly, `SameSite=Lax` cookie, `Secure` with the `__Host-` prefix over TLS; the database holds its SHA-256 and passwords as argon2id hashes. Scripts and agents use personal API tokens instead: a person signed in creates one with a name, and the request sends it as `Authorization: Bearer <secret>`, which wins over a session cookie; an `Authorization` of another scheme, such as a reverse proxy's Basic credentials, leaves the cookie to decide. The secret is a random token like a session's, shown once; the database holds its SHA-256. A token acts as its owner until it is revoked; a read-only one may make only the requests the model marks `@readonly`, which are its GET requests, since Smithy's validation pairs the two; and no token may create or revoke a token or sign out, so a leaked one cannot outlive its revocation. The model declares bearer authentication, optional on every operation that takes a session too, so the generated client sends a token when it has one and the OpenAPI document tells scripts how; two model validators keep every operation declaring one of the server's two modes and pair GET with `@readonly` for every operation a token may call. Every management operation but the five that start a session needs a session or a token, and a resource of another account answers as a missing one does. An account owns devices, screens and tokens; there are no roles.
